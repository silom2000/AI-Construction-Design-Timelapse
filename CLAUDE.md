## Принципы (Karpathy & Superpowers Guidelines)

- **Обязательный мозговой штурм (Mandatory Brainstorming)**
  - Выдерживай паузу перед написанием кода. Делай шаг назад и уточняй, какую *конечную* цель мы преследуем.
  - Явно проговаривай предположения и trade-offs. 
  - Если есть несколько вариантов решения — предложи их, не выбирай молча, спроси пользователя.
  - Если задача кажется запутанной — остановись. Назови то, что непонятно, и задай вопрос. 

- **Строгий TDD (Test-Driven Development)**
  - Цикл Red-Green-Refactor обязателен. ВСЕГДА сначала пиши падающий тест, и только потом бизнес-логику для него.
  - Удаляй любой код, написанный до тестов.

- **Микро-планирование (Granular Task Planning)**
  - Режь большие задачи на микро-шаги по 2-5 минут каждый.
  - Для каждого шага фиксируй: точные файлы для изменения, сниппеты кода, и строгие критерии проверки (как мы убедимся, что шаг выполнен?).

- **Двухэтапная проверка (Two-Stage Reviews)**
  - Сначала проверяй реализацию на соответствие бизнес-требованиям (работает ли алгоритм), и только затем — на качество кода.
  - Обнаружение критических багов автоматически блокирует дальнейшую разработку до их полного исправления.

- **Простота превыше всего (Simplicity First)**
  - Код должен быть минимальным. YAGNI (You aren't gonna need it) и DRY. Читаемость > «умный» код.
  - Никакого кода "на будущее". Никаких абстракций для одноразового использования.
  - Если ты написал 200 строк, а можно было 50 — перепиши.

- **Хирургические изменения (Surgical Changes)**
  - Делай минимум диффа. Меняй ТОЛЬКО то, что абсолютно необходимо для задачи.
  - Не "улучшай" соседний код, форматирование или комментарии. Не рефактори то, что не сломано.
  - Подстраивайся под существующий стиль кода, даже если сам написал бы иначе.
  - Убирай за собой: удаляй импорты и функции, которые стали не нужны из-за *твоих* изменений.

- **Целеполагание (Verify before declaring success)**
  - Процесс важнее угадывания. Проверяй работоспособность *до* того, как отрапортуешь об успехе.

- snake_case / PascalCase

- 4 пробела

## Хорошие практики

- Маленькие функции с одной ответственностью
- Early return
- Context managers (`with`)
- `logger` вместо `print()`
- Явная обработка ошибок + осмысленные исключения
- Секреты только через `.env` + `python-dotenv`
- `dataclasses` для простых моделей, **Pydantic** для валидации/API

## aiogram 3.x (обязательные правила)

- **Всё асинхронно** (`async def` + `await`)
- Используй **Router** для модульности (не лепи всё в один файл)
- Регистрируй handlers через `@router.message()`, `@router.callback_query()` и т.д.
- Handlers должны быть тонкими: только валидация + вызов service слоя
- Используй **Magic Filters** (`F.text`, `F.photo`, `Command()` и др.)
- Для состояний — **FSM** (`aiogram.fsm`)
- FSM — только для пользовательских сценариев, не для бизнес-логики
- Middlewares: `BaseMiddleware` или async callable (outer/inner)
- Bot создавай с `DefaultBotProperties(parse_mode=ParseMode.HTML)`
- `asyncio.run(main())` + `dp.start_polling(bot)`
- Никогда не используй глобальные `Bot.get_current()` (передавай `bot: Bot` явно)

## Workflow с GPT/Claude

1. Сгенерируй простую рабочую версию
2. Упрости и почисти (Karpathy style)
3. Добавь типы, docstrings, логирование
4. Зафиксируй критерии проверки (что должно произойти, чтобы задача считалась выполненной?)
5. Для многошаговых задач строй мини-план: `Шаг 1 -> проверка; Шаг 2 -> проверка`. Напиши тесты.
6. Прогони:
```bash
uv run ruff check .
uv run ruff format .
uv run mypy .
uv run pytest
```
Git Bash неправильно интерпретирует /PID. Используй PowerShell
